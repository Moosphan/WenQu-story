# WenQu：面向数百章续写的有界上下文与长期记忆方案

研究日期：2026-09-14。状态：已开始分期实施，默认 shadow；已有构造 100/300/500 章历史快照回放，尚未完成真实长篇质量与成本验收。详见 [实施进度与限制](18-bounded-context-implementation-progress.md)。运行中的写作服务未修改。

## 已确认的实施修订（优先于后文初始预算参数）

用户担心固定窗口造成新失败，已确认先测量再逐步启用。后文 24K 是待校准的起始目标，不是所有章节的统一拒绝阈值；分层数额均为可借用的软配额。采用“软目标 + 弹性空间 + 模型实际容量硬保护”，复杂章节可在实际模型容量和费用预算内扩大工作包。最终输入、输出预留和其他开销不能超过实际可用窗口。

先做只测量、不拦截的 shadow 模式，回放写作、返修、审稿、抽取的历史请求；已有传输/容量保护仍保留。分别统计自动整理触发率、整理后仍不可执行比例、输出截断、关键事实遗漏和每章总消耗，不能把整理触发算作失败。没有样本前不承诺具体失败概率。

去重、版本过滤、状态选择与配额再分配优先本地完成，不默认增加 AI 压缩调用。不得因新的预算策略拒收已生成的合格正文。只有必要内容实际放不下时才受控补查或按自然场景处理；不得静默丢硬约束，不得无限重试。分阶段验证通过后再启用自适应装箱，保留回滚开关。

## 1. 结论

长期资料保存在数据库，每次模型调用只读取一个有明确容量上限的“本章工作包”。用稳定实体、当前状态、伏笔调度、混合检索和原文溯源保证可追忆；用独立的上下文编译器保证请求不随章节数增长。

应控制的是**单次输入和每章调用次数**，不是要求数据库不增长。保存几百章正文和历史事件，存储随章节线性增长是合理的。若每次都带全部历史，单次输入近似 O(N)，写完 N 章的累计输入可能接近 O(N²)；这不必然是指数增长。

固定上下文不可能保证任意细节永不遗漏。可实现、可验收的目标是：原文不丢、已标注的关键约束可靠召回、普通细节按需查证、不确定时不编造、请求永不无界增长。

## 2. 当前实现为什么膨胀

检查位置：`story_core/memory.py` 的 `canonical_memory`、`context_layers`，以及 `story_core/service.py` 的任务上下文组装。

| 当前行为 | 长篇后果 | 改造方向 |
|---|---|---|
| 所有 open promise 列入 required | 几百章埋下的伏笔反复发送 | 只有到期、触发或本章明确依赖的伏笔进入工作包 |
| 历史记忆出现参与人物名字便列入 required | 主角几乎关联整部小说 | 读取人物当前状态，历史事件另外检索 |
| 较宽松的题纲词匹配即可列入 required | 普通修仙词汇召回大量旧事件 | 相关性决定候选排名，不直接等于不可删除 |
| 只限制 supplementary 条数 | 必读层及单条长度仍无限制 | 每个通道和总请求同时限制 token |
| 按 kind、文字 key、owner 合并记忆 | 同义改写形成重复事实 | 稳定实体 ID、规范谓词、状态投影 |
| 整份 brief、全部 planned_promises 入参 | 全书规划逐渐成为隐性长历史 | 核心约定常驻，人物与规划按本章裁剪 |
| 以 180000 UTF-8 字节作为主要请求门槛 | 与模型真实上下文容量不一致 | 模型 token 预算为主，字节限制仅保护传输 |

近期去掉重复来源引文、前端展示元数据能降低体积，但没有改变 required 层的增长规律。下一步应重构选择规则，不能继续仅靠删字段或提高阈值。

## 3. 开源项目参考与选型

以下借鉴的是工程机制，不是认定这些项目已经解决长篇小说的一致性问题。

| 项目及一手来源 | 值得借鉴 | WenQu 的使用边界 |
|---|---|---|
| [LangGraph / LangChain Memory](https://docs.langchain.com/oss/python/concepts/memory) | 线程短期状态和跨线程长期记忆分离；长期记录按 namespace/key 管理；区分同步写入与后台整理 | 保留已有 SQLite 任务机制，借鉴分层和检查点，不必整体迁移框架 |
| [Graphiti](https://github.com/getzep/graphiti) | 时间化实体关系、事实来源、增量更新，结合语义、关键词和图关系检索 | 适合后期跨角色关系检索；图数据库与模型抽取增加运维及校验成本，不能自动充当小说事实裁判 |
| [LightRAG 查询参数源码](https://raw.githubusercontent.com/HKUDS/LightRAG/main/lightrag/base.py) | 分别限制实体、关系、文本召回，并设置 max_total_tokens 总预算 | 借鉴“检索后仍要预算装箱”；设置 top-k 本身不足以控制请求长度 |
| [Letta / MemGPT](https://github.com/letta-ai/letta)、[V1 memory blocks 文档](https://docs.letta.com/v1-sdk/memory/memory-blocks) | 小型常驻记忆与外部长期资料分离 | 此处参考记忆分层思想。仓库明确 V1 服务已退役，当前源码转向 letta-code；不以旧教程 API 直接搭建新系统 |

推荐：**SQLite 版本化事实库 + WenQu 自有上下文编译器 + 可替换检索适配器**。先做稳定性和预算，再按实测引入向量检索或 Graphiti。没有必要同时接入四套框架。

## 4. 六层记忆结构

### 4.1 原文与事件档案：永久保存，默认不整批发送

保存每章正文、版本、用户确认、事实变化和来源段落。旧版本保留但不参与当前正文的普通检索。摘要、向量、图谱均是可重建索引，不是唯一事实来源。

### 4.2 当前状态：用状态替代历史流水账

为人物、物品、地点、组织分配稳定 ID。姓名和别名只是显示属性，改名不产生新人物。

例如主角“持有灵石”的当前状态只发送最新有效数量和必要来源；获得、花费的完整流水保存在事件表，需要核账时再查。伤势、境界、位置、物品归属、契约均使用明确谓词，而不是不断追加一段人物摘要。

当前状态也不能全量发送：只加载本章角色及直接相关实体。单实体字段和文本长度同样受预算约束。

建议事实字段：

```text
book_id / branch_id
fact_id / subject_entity_id / predicate / object_or_value
scope: objective | character_belief | author_plan
owner_entity_id
story_valid_from / story_valid_to
known_from_chapter / revealed_from_chapter
source_chapter / source_version / source_paragraph
recorded_revision / superseded_by / verification_status
```

故事内时间和章节序号分开：倒叙中出现的事实不一定发生在当前时间。“角色以为某人已死”不能覆盖“此人实际存活”。计划中的未来事件也不能写成已经发生。

### 4.3 伏笔与义务：数据库调度，不依赖语义搜索碰运气

伏笔使用稳定 promise_id，记录铺垫章节、参与实体、触发条件、预计回收区间、重要级别及状态。

状态至少包含 dormant、active、due、resolved、cancelled。每次组装查询：本章到期项、本章事件触发项、本章计划明确引用项；遥远伏笔留在库中。

没有明确回收章节的伏笔关联卷目标或触发事件，并进入定期全书检查队列，不能简单过期删除。到期项过多时先调整本章场景/规划或显式提示用户处理，不允许静默截断。

### 4.4 分层摘要：帮助定位，不替代证据

保存定长章摘要、固定规模卷/篇章摘要、定长全书主线。全书主线聚焦当前方向、已完成转折和开放目标，不把历章摘要不断拼进去。

生成摘要时可追溯到事实 ID 和原文章节。更新摘要时从事件和原文取依据，避免长期反复“摘要的摘要”累积漂移。摘要中的历史信息被压缩掉，只代表不常驻，原文及事件索引仍在。

近期承接通常取上一章结尾原文及近两章简要事件；遇到对话直接续接等情况再增加局部原文，无须默认发送两章全文。

### 4.5 混合检索：找回与当前场景有关的旧事

先根据本章计划列出人物、地点、物品、待解问题和伏笔 ID，再走几个有界通道：

1. 精确 ID 查询：当前状态、到期义务、明确引用的历史事实。
2. 关键词检索：人名、别名、独特物品、原话。中文需分词或适当字符索引，不能假设默认英文式分词有效。
3. 语义检索：措辞变化但含义相关的历史场景。
4. 关系扩展：最多限定跳数和邻居数，找交易双方、物品持有人等直接依赖。

候选融合、去重、重排后，交给上下文编译器。检索结果必须携带来源，限制单事件占比，避免重复场景占满预算。作品、分支、有效版本、时间边界、任务可见性过滤须覆盖检索和每次关系扩展。

作者规划可以包含未来秘密，角色视角正文不能直接知道秘密。不同任务需要明确权限视图，不能仅靠一句“不要剧透”的提示词。

### 4.6 本章工作包：唯一模型输入出口

所有 GUI、CLI、MCP、宿主插件通过同一 ContextCompiler 获取模型输入。各宿主不再自行拼接一套历史，也不能把上一次完整请求嵌入下一次请求。

工作包包括本章目标、必要约定、当前状态、相关义务、近期承接、历史证据，以及本阶段规范。来源面板等完整诊断信息留在应用内，模型只接收短引用 ID 和必要原文。

## 5. 固定预算设计

下表是建议起始参数，需根据所选模型和离线回放校准，不是开源项目推荐值或已验证性能。

| 写作输入组成 | 建议上限（tokens） |
|---|---:|
| 系统指令、输出结构及本阶段写作规范 | 3000 |
| 核心故事约定、主线定位 | 1500 |
| 本章计划、相邻规划 | 2000 |
| 当前人物与物品状态 | 3000 |
| 活跃伏笔、契约、禁止矛盾项 | 2000 |
| 近期承接原文与摘要 | 3500 |
| 检索历史证据 | 5000 |
| 估算误差及临时补查预留 | 4000 |
| **总输入软目标（以已确认修订为准）** | **24000，允许借用与扩展** |

输出另预留例如 8000 tokens。只有模型实际可用窗口能容纳“最终输入 + 输出预留 + 额外开销”时才采用该配置；窗口较小则降配。正文汉字数和 token 数不能视为相等。

返修、审稿、抽取有各自预算：返修优先保留当前稿和具体修改项；审稿只取当前稿与相关约束；记忆抽取以本章正文、实体别名和少量候选旧事实为主，不应读取全部世界记忆。阶段预算不能简单叠加到一个超大请求里。

计数须针对最终序列化消息、schema、工具定义等。优先使用对应 tokenizer；没有可靠 tokenizer 时采用经过样本校准的保守估算及余量，页面标记“估算”，不能把 UTF-8 字节标成精确 token。模型账单用量另行记录。

### 超预算处理顺序

1. 去重和去掉展示元数据。
2. 合并同一事实，移除已失效状态与非本章资料。
3. 降低可选召回量，将长引文替换为短证据及可补查指针。
4. 在保留硬约束的前提下重新装箱。
5. 若关键约束本身过多，拆分有限场景或定向检查；仍不可容纳则给出具体冲突和规划调整入口。

不能悄悄丢掉硬约束，也不能重复发送同一个超限请求。按需补查必须替换工作包里的可选内容并重新计数，而不是无限追加聊天记录。建议每章最多 2 次补查，超出进入明确的待处理状态。

## 6. 第 350 章如何记得第 12 章

示例：第 12 章主角借出铜牌，第 350 章回到原城讨债。

本章计划引用地点和债务对象，精确关系查询获得未履行契约；伏笔调度提供对应 promise_id；系统取铜牌当前归属、契约条件、第 12 章相关段落和中途是否归还的事件。把这些放进几百到数千 tokens 的历史证据区，不读取中间 338 章。

如果原规划没有显式提债务，人物与地点关系召回可以补充线索；如果连关系都未被抽取，语义检索仍可能找到原文，但不能保证必然找到。因此必须对重要伏笔做显式标注，并通过长距离召回测试衡量遗漏。

模型遇到不确定数量、日期、原话时先查询，不按模糊摘要猜测。未找到资料表示“未知”，不表示“从未发生”。

## 7. 记忆写入、改章与审核收敛

### 增量提交

候选稿记忆保存在候选命名空间，不进入正式世界状态。最终提交正文时，将版本指针、可用事实变更、下一任务检查点纳入一致的提交过程。向量等辅助索引可后台更新，但后续任务须知道索引水位，并通过精确查询覆盖尚未索引的新事实。

模型提出事实变更，服务端验证来源与类型；冲突项保留为待核实，不因模型最新说法自动覆盖事实。非关键抽取项失败可记录为隔离项并降级到原文，不能无限重试；影响下一章硬约束的缺项必须补查或定向修复。

### 修改旧章节

维护正文版本到事实、状态、摘要和检索索引的依赖关系。旧章修改后失效相关派生项，而不是继续召回旧向量；后台重建受影响范围。依赖未修复的续写设置一致性屏障，避免边改名边使用旧设定继续写。

改名主要更新实体显示名称和别名；是否替换历史正文由作品编辑策略决定，不能改变实体身份。未受影响资料无需全书重算。

### 审核基线固定

每章保存 context_fingerprint、正文版本和 review_policy_version。返修审稿重点核对既有问题是否解决、是否引入新问题；只有明确的新证据才能引入新的严重阻断项，不能每次随机换一套口味。

遵循已有用户要求：单章内容审核最多 3 次，达到上限按策略通过并标注遗留问题；单章人工确认与连写默认确认分开。格式错误、网络错误采用独立且有限的技术重试计数，不能重置内容审稿次数。无可用正文的传输失败不能伪装为审核通过。

缓存仅在正文、约定、所依赖事实与审核标准均未变化时复用。保留失败原始结果，能够确定性修复/重放的格式问题不重新生成整章。

## 8. 可插拔接口

```text
VersionedManuscriptStore：正文和不可变版本
MemoryStore：事实、实体、状态、义务与来源
StateReducer：已验证事件 → 当前状态
Retriever：关键词 / 向量 / 图 / 精确查询
ContextCompiler：阶段视图、优先级、预算与装箱
TokenCounter：对应模型计数或标注过的保守估算
GenerationProvider：Claude / DeepSeek / 其他宿主
```

先基于现有 SQLite 实现接口。可选向量或图后端通过 Retriever 接入，不掌握正文提交权。Skill 提供任务规范和知识需求；由核心服务决定可见性、预算、版本与提交。这样替换模型、Skill 或宿主时，记忆与续写进度仍由 WenQu 保持。

## 9. 复杂度和成本边界

设每章正文、事实数量、每次输入预算 B 与每章模型调用上限 C 均有界：

- 原文及事实存储随 N 增长，约 O(N)；大量手工版本会额外增加存储。
- 每次模型输入最多 B，不随 N 增长。
- 写作/审稿/补查累计输入上界约 N × C × B，即 O(N)。
- 该结论依赖调用上限实际执行；无限重试或持续全书重建会破坏它。
- 检索延迟取决于索引与候选数量。当前全量读入 Python 打分也要改，否则模型上下文不长，服务端仍会越来越慢。
- 分层摘要若每章重算整棵层级，会增加后台成本；优先局部增量更新、固定规模卷归档，单独统计维护开销。

不能承诺任意长书、任意多角色、任意复杂单章都在同一预算内零遗漏。可以承诺预算受控，以及无法满足硬依赖时明确说明，不把失败隐藏在模型反复返修里。

## 10. 分期落地

| 阶段 | 工作 | 完成标准 |
|---|---|---|
| P0：测量与受控装箱 | ContextCompiler、阶段软目标、required 规则重写、brief/promises 裁剪、上下文组成诊断 | 默认 shadow 不新增拦截；自适应模式在实际容量内保留硬依赖；完成离线回放后逐步启用 |
| P1：状态化记忆 | 实体 ID、规范事实键、状态投影、伏笔调度、版本失效关系 | 改名、契约履行、伤势变化、旧章重写不产生错误活跃事实 |
| P2：提高远期召回 | 中文关键词索引、可选语义检索、受控关系扩展、有限补查 | 长距离伏笔与同义线索测试达标；不串书、不泄露视角外信息 |
| P3：长篇验证 | 100/300/500 章测试集、复杂度与成本报告、可选图后端评测 | 单次上下文曲线有上限；质量达到预设门槛后才迁移真实连写 |

优先不重写整个编排框架。P0 直接替换当前内存选择和组装路径；P1 再迁移数据结构。旧记录保留来源，逐批补充稳定 ID，无法确定的实体合并交由人工确认。

## 11. 验收与可观测性

以下是建议验收目标，不是已获得的测试成绩：

| 指标 | 建议目标 |
|---|---|
| 最终请求 token | shadow 先测量；自适应模式输入+输出预留+其他开销不超过已配置实际容量，阶段额度为软目标 |
| 章数扩大后输入长度 | 100→300→500 章不出现随历史持续上升的趋势 |
| 人工标注的硬依赖召回 | 测试集 100%，缺项不能静默发送 |
| 普通长距离相关线索召回 | 初始目标 ≥95%，另报告误召回与成本 |
| 串书、失效版本、视角泄露 | 测试集零违规 |
| 内容审稿 | 每章最多 3 次，技术失败不重置次数 |
| 同输入失败重试 | 有明确上限，不能循环消耗 |

测试覆盖：数百章后回收旧伏笔、主角更名和化名、谎言与真实事实、倒叙、物品多次转手、旧章修改、超多同名实体、同义重复记忆、同时到期的多个义务、暂停恢复和索引滞后。

先使用现有授权正文与构造测试集做离线回放，不必付费生成 500 章才能验证预算。对比“全历史”“只摘要”“只向量”“有界混合检索”，分别统计召回和请求体积；之后用小规模真实续写检查文风与衔接。

页面展示本章上下文用量/上限、各层占比、历史引用来源、关键义务覆盖率、索引水位和漏项原因。财务累计 token、当前请求 token、输出预留分开，避免用户误以为增加总预算就能解除上下文限制。

## 12. 决策建议

下一步先完成 P0 和 P1。向量库、图谱、超大窗口模型可以增强检索或承载能力，但无法代替“当前状态取代历史流水账”“义务调度”“最终请求预算”这三项基础机制。

本方案的目标是：越写资料越完整，每次实际读入仍保持有限；重要旧事通过结构化索引和原文找回，而不是要求模型持续背诵整部小说。
